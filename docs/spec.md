# vulhub-cli 一期

## Problem Statement

小团队共用一台 Linux 机器做漏洞复现，靶场全部来自 vulhub。vulhub 提供的靶场数量很多，但它的"管理 & 运维"能力很薄弱：想知道有哪些靶场要翻目录树；想启动一个靶场要先 `cd` 进它的目录再敲 `docker compose`；起完之后想清理，又得记住它到底叫什么名字。

一两个靶场时这些都不是问题，几十上百个之后逐个手工操作就不可行了。更麻烦的是团队共用一台机器——谁起了什么、哪些还开着，没有统一的视图。

## Solution

一个 linux-amd64 的静态二进制 `vulhub-cli`。用户拿到它即可使用，不需要安装运行时。

它先用 `init` 把 vulhub 拉到本地（`update` 负责后续更新），然后就能查询靶场、启动靶场、暂停靶场、销毁靶场。每个靶场都可以用**编号**或**路径**指代。

## User Stories

1. 作为一个刚拿到这个工具的团队成员，我想要一条 `init` 命令就把 vulhub 拉好，以便不用手工 clone 和配路径。
2. 作为一个刚拿到这个工具的团队成员，我想要 `init` 在我机器缺少 `git` 时明确告诉我缺的是 `git`，以便我不必自己猜为什么失败。
3. 作为一个刚拿到这个工具的团队成员，我想要 `init` 在我机器缺少 `docker` 时明确告诉我缺的是 `docker`，以便我不必自己猜为什么失败。
4. 作为一个刚拿到这个工具的团队成员，我想要 `init` 在 `docker compose` 和 `docker-compose` 都不存在时报错、任一存在时都能正常工作，以便我不必为了这个工具去调整我的 Docker 安装方式。
5. 作为一个已经初始化过的用户，我想要再次运行 `init` 时它报错并提示我改用 `update`，以便它不会把我已经拉好的 vulhub 覆盖掉。
6. 作为一个已经初始化过的用户，我想要 `init` 完成后编号就已经分配好，以便我立刻就能用 `up 68` 而不必先跑一次 `ls`。
7. 作为一个使用者，我想要 `ls` 列出全部靶场并给出编号、路径和漏洞标题，以便我一眼看清这个机器上有哪些靶场。
8. 作为一个使用者，我想要 `ls` 的输出分页显示（先 20 行，之后每按回车多一行），以便上千个靶场不会把我的终端刷屏。
9. 作为一个使用者，我想要 `ls` 在被管道接走时自动关闭分页，以便 `vulhub ls | grep xxx` 不会挂住。
10. 作为一个使用者，我想要 `search <关键词>` 按漏洞标题和靶场路径检索，以便我既可以用"log4j"这样的软件名找，也可以用"CVE-2021-44228"这样的编号找。
11. 作为一个使用者，我想要 `search` 对大小写不敏感，以便我不必记住标题里哪个字母是大写的。
12. 作为一个使用者，我想要 `search apache rce` 要求两个词都命中，以便结果集足够小、能直接看。
13. 作为一个使用者，我想要 `search` 无命中时返回非零退出码，以便我在脚本里能判断"没找到"。
14. 作为一个使用者，我想要 `up <编号>` 启动一个靶场，以便我不必 cd 进目录再敲 compose 命令。
15. 作为一个使用者，我想要 `up <路径>` 和 `up <编号>` 效果完全相同，以便我在记不住编号时仍能精确操作。
16. 作为一个使用者，我想要 `up` 在后台启动并把缺失的镜像自动拉下来，以便我不用关心镜像是否已存在。
17. 作为一个使用者，我想要 `up` 成功后打印这个靶场的所有访问地址（含端口和本机内网 IP），以便我不用自己去查端口、也不用猜队友该访问哪个 IP。
18. 作为一个使用者，我想要 `up` 遇到端口冲突时直接让 Docker 报错，以便工具不会自作聪明地替我改端口、产生一个和我预期不符的环境。
19. 作为一个使用者，我想要 `up` 支持逗号分隔的多个靶场，以便我一次起好几个。
20. 作为一个使用者，我想要 `stop <靶场>` 停止一个靶场，以便我暂时释放它占用的资源。
21. 作为一个使用者，我想要 `stop` 支持多个靶场，以便我批量暂停。
22. 作为一个使用者，我想要 `del <靶场>` 删除它的容器和网络但保留 volume，以便我误删时数据还在、重起就能恢复。
23. 作为一个使用者，我想要 `del` 在动手前打印它将要删除的靶场编号、靶场路径、compose 项目（网络随该项目一并删除）和涉及的容器，并要求我输入 `y` 确认，以便我不会因为手滑而误删。
24. 作为一个使用者，我想要 `del -y` 跳过确认，以便我在脚本里能非交互地清理。
25. 作为一个使用者，我想要 `del -a` 连这个靶场的 volume 和它引用的镜像一起删掉，以便我用一个选项就能彻底清干净，而不必记住两个 flag。
26. 作为一个使用者，我想要 `del -a` 只删这一个靶场引用的镜像、不去做全局清理，以便工具不会波及 vulhub 之外我自己的镜像。
27. 作为一个使用者，我想要 `del` 拒绝一次删除多个靶场，以便这个不可逆操作不会被批量执行。
28. 作为一个使用者，我想要 `status` 显示当前机器上所有运行中的容器，并按靶场分组，以便我一眼看清"现在开着哪几个靶场"而不是"开着哪些容器"。
29. 作为一个使用者，我想要 `status` 只在容器是由 compose 创建时才显示它，以便它展示的是靶场而不是这台机器上的所有杂项容器。
30. 作为一个使用者，我想要 `status --json` 输出结构化数据，以便我把靶场状态接进自己的监控脚本。
31. 作为一个使用者，我想要 `ls --json` 输出结构化数据，以便我在脚本里解析靶场清单。
32. 作为一个使用者，我想要 `pull <靶场>` 单独拉取镜像，以便我把"拉镜像"和"起容器"分开，在网络慢的时候先拉好。
33. 作为一个使用者，我想要 `pull 1,2,68` 一次拉多个靶场的镜像，以便我为一次演练集中准备。
34. 作为一个使用者，我想要 `pull --all` 拉取全部镜像，以便我在断网演练前把要用的都准备好。
35. 作为一个使用者，我想要 `--all` 必须显式指定、不能是默认行为，以便我不会因为手滑而触发几十 GB 的下载。
36. 作为一个使用者，我想要 `update` 更新本地的 vulhub，以便我拿到上游新增的靶场。
37. 作为一个使用者，我想要 `update` 在遇到本地改动冲突时报错并原样打印 git 的输出，以便工具不会自动合并或覆盖、把我的改动弄丢。
38. 作为一个使用者，我想要 `update` 不阻止正在运行的靶场，但在结束后提示哪些靶场受影响需要重启，以便我不会在不知情的情况下继续用一个已被更新的环境。
39. 作为一个使用者，我想要 `update` 新增的靶场被追加到编号末尾，以便我之前记住的编号不会失效。
40. 作为一个使用者，我想要 `update` 删掉的靶场其编号作废且不再被分配给别的靶场，以便"68 号"在同事之间可以放心口头传达。
41. 作为一个使用者，我想要索引文件损坏或丢失时工具能自动重建它，并明确警告我编号已重新分配，以便我不会在不知情的情况下用错编号。
42. 作为一个使用者，我想要索引里指向的靶场路径不存在时工具静默跳过而不报错，以便 `update` 删除靶场这种正常事件不会产生噪音。
43. 作为一个使用者，我想要在编号记混时还能用路径精确操作，以便工具不会因为索引出问题而变得不可用。
44. 作为一个使用者的队友，我想要这个工具不区分是谁在操作，以便我们共用一台机器时不需要额外配置账号或权限。
45. 作为一个使用者的队友，我想要这个工具不去枚举网卡以外的机器环境，以便它在我和同事的机器上行为一致。
46. 作为一个使用者，我想要 `del` 在无法确认靶场运行状态时直接中止，以便它不会在不可逆操作之前打印"当前没有运行中的容器"、让我误以为无东西可删。
47. 作为一个使用者，我想要 `search --json` 输出结构化数据，以便检索结果能直接喂给脚本。
48. 作为一个使用者，我想要 `help` 打印用法，以便我不必去翻文档就能记起命令怎么用。
49. 作为一个使用者的队友，我想要同一个错误在所有命令上返回同一个退出码，以便我写的脚本不必为每个命令记住一套规则。
50. 作为一个使用者的队友，我想要 `update` 不把检出之外的 compose 项目报成"受影响的靶场"，以便它的提示只关于靶场。

## Implementation Decisions

### 交付形态

单一 linux-amd64 静态二进制。不产出 macOS / Windows / ARM 版本。

### 命令表面

`init`、`ls`、`search`、`up`、`stop`、`del`、`status`、`pull`、`update`、`help` 十个命令。

`<靶场>` 参数接受靶场编号或靶场路径，两者等价。

逗号分隔的多选**只适用于 `pull`、`up`、`stop`**；`del` 是唯一不可逆的操作，不接受多选。

`--json` 适用于三个列表命令：`ls`、`search`、`status`。

**退出码**：`0` 成功；`1` 运行失败（靶场不存在、Docker 报错、`search` 无命中）；`2` 用法错误（参数数量不对、未知选项）。**同一类错误在所有命令上必须返回同一个码**。

### 靶场的寻址：路径是身份，编号是别名

靶场路径是唯一身份标识；靶场编号是它的别名。这个主从关系是刻意的——编号由工具自己发出，vulhub 上游并不知道它，索引重建时编号会重新分配。路径作为身份保证了编号失效时工具不会变得不可用。

一个靶场最多只有一份运行中的实例：一份 vulhub 检出对应一套固定的 compose 项目名。

### 索引

索引是靶场路径到靶场编号的持久映射，是工具唯一需要持久保存的状态。

- 存放位置在 `~/vulhub` **之外**（`~/vulhub` 是 git 仓库，索引写进去会产生未跟踪文件，使 `update` 的 `git pull` 面对脏工作区）。
- 编号在 `init` 完成后**立即**按靶场路径字典序一次性分配。选字典序是因为它完全由本地目录决定、可复现，索引重建时能还原出基本一致的编号。
- 编号一旦分配就不随 vulhub 更新改变；新靶场追加到末尾；消失的靶场其编号作废、不复用。
- 索引中的路径在 vulhub 检出里不存在时静默跳过。
- 索引丢失或损坏时自动重建，但必须打印醒目警告，说明编号已重新分配。

### 靶场目录（Catalog）

靶场清单**优先解析 vulhub 检出根目录的 `environments.toml`**（vulhub 官方的环境注册表，含 `name`/`cve`/`app`/`path`/`tags`/`dockerfile` 字段，由上游 CI 校验其与真实目录一致）。

**该文件缺失或解析失败时降级为扫描目录树**，此时只能得到靶场路径，`ls` 与 `search` 的标题列为空。

`search` 检索 `name` 与 `path` 两个字段：`path` 恰好包含软件名与 CVE 号，因此软件名、CVE 号、漏洞标题三类最常用的检索词被两个字段全覆盖，且在降级路径下同样可用。

### 靶场识别

判断"某个容器属于哪个靶场"靠 **compose 自动打上的标签**（`com.docker.compose.project` 与 `com.docker.compose.project.working_dir`），后者的绝对路径砍掉 vulhub 检出根目录前缀即为靶场路径。

**不靠容器名反推**：官方 vulhub 的 compose 文件基本不写 `container_name`，容器名实为 compose 自动生成的 `<项目名>-<service>-<序号>`，解析它等于依赖 compose 的实现细节。

代价是 `status` 只能看见由 compose 创建的容器。

一个靶场对应一个 compose 项目，无论它内含几个容器；`up`/`stop`/`del` 一律作用在整个项目上，单容器情形是 N=1 的退化，代码无需特判。

**只有工作目录落在 vulhub 检出之内的容器才算靶场。**这台机器上别人的 compose 项目不在检出内，必须被排除在靶场语义之外——否则 `update` 会把它们报成"受本次更新影响的靶场"。`status` 仍然显示它们（它看的是全机），只是不把它们按靶场归组。

### 外部依赖的调用方式

工具通过**调用 `docker compose` 命令行**操作容器，不使用 Docker SDK。运行期探测 `docker compose`（v2）与 `docker-compose`（v1）哪个可用。

`init` 的前置检查要求 `git` 与 `docker` 存在，且上述两者至少有一个存在。

### 模块划分

- **命令层**：解析参数、分发到各命令、把结果写到输出流、决定退出码。
- **靶场目录**：产出靶场清单（路径 + 可选标题），含 `environments.toml` 解析与目录扫描两条路径。
- **索引**：读写编号映射，负责分配、追加、作废、重建。
- **编排端口**：对某个靶场目录执行 up / stop / down / pull，以及查询全机容器及其 compose 标签。
- **git 端口**：clone 与 pull。
- **主机端口**：提供本机可用于外部访问的 IP。
- **输出**：分页渲染、表格渲染、JSON 渲染。

### 需要被替换的外部依赖

只有三个外部依赖需要抽象成端口，其余一律使用真实实现（见测试决策）：

- **编排端口**：真实实现会跑起 Docker，慢且需要 daemon。
- **git 端口**：真实实现要联网拉取数百 MB。
- **主机端口**：返回值取决于运行环境，测试中必须可控。

vulhub 检出根目录的路径必须是**可注入的配置值**（而非硬编码），这是让文件系统与 `environments.toml` 解析得以使用真实实现的前提。

## Testing Decisions

**好的测试只断言外部行为，不触碰实现细节。**对这个工具而言，"外部行为"就是从命令行进、从输出流和退出码出——所以测试的断言对象只有三样：写到输出流的内容、被调用的外部依赖（编排 / git / 主机）、以及退出码。测试不应断言内部函数、不应断言中间数据结构、不应断言调用了哪个私有方法。

**唯一的测试缝**是 CLI 的入口函数，形态上等价于：

```
Run(args []string, in io.Reader, out, errOut io.Writer, isTTY bool, deps Deps) int
```

这是能开在的最高点。它下面的一切都是实现细节，测试碰不到。

**用真实实现而非假对象的依赖**：

- **文件系统**：索引文件写在临时目录里的真实文件上，测的是真的读写与序列化。vulhub 检出根目录指向临时目录即可。
- **`environments.toml` 解析**：用临时 fixture 目录喂真实解析器。同样，测真解析比测假对象有价值——它顺带覆盖了降级路径。

**用假对象的依赖**：编排端口、git 端口、主机端口，理由见实现决策。

**本项目尚无既有测试**（工程目录里目前只有文档与 `go.mod`），因此没有可直接复用的先例。测试应建立在本项目自己的约定之上。

**端到端的冒烟测试**（真实二进制 + 真实 Docker）单独存在、不进主测试套件。它是第二道缝，只在发布前手工运行。主测试套件跑得快，才是它有价值的前提。

## Out of Scope

- **多用户隔离与权限**：不区分调用者，不做"只能操作自己创建的靶场"。共用一台机器的人被视为同一套部署。
- **端口冲突预检**：交给 Docker 报错。
- **镜像清理**：不做 `docker image prune`，不做跨靶场的镜像共享检查。
- **交互式选择器**：`up` 只接受显式参数，不支持模糊匹配或方向键选择。
- **`info` / `logs` / `exec` 命令**：一期不做，用户可自行 `docker compose logs`。
- **`ls` / `search` 的字段限定**（如 `--cve`、`--tag`）：等实际使用中觉得吵了再加。
- **非 linux-amd64 平台**。
- **配置文件**：vulhub 检出位置固定，不提供配置文件。

## Further Notes

### 一期发布前应确认的未验证项

以下事实未被直接证实。每项都已在设计中留有退路。

| 项 | 影响 | 退路 |
|---|---|---|
| `environments.toml` 是否存在于 vulhub 主分支 | 决定 `ls`/`search` 能否显示标题、能否按 CVE 搜 | 降级为扫描目录树 |
| vulhub 的靶场总数（量级判断为千级） | 影响 `ls` 的可读性 | 已用分页缓解 |
| 是否每个靶场都恰好一个 `docker-compose.yml` | 影响 `up`/`pull` 的实现 | 若有环境含多个 compose 文件，需明确取舍规则 |
| vulhub 仓库的克隆体积 | 影响 `init` 的耗时预期与是否需要进度提示 | 已选 `--depth 1` 压低体积 |

### 已核实的事实

记录在此避免重复怀疑：

- `environments.toml` 采用 `[[environment]]` 数组格式，字段为 `name` / `cve` / `app` / `path` / `tags` / `dockerfile`。
- vulhub 的 compose 文件**写死宿主端口**（形如 `"8080:80"`），因此 `up` 打印访问地址是可行的。
- **多 service 环境确实存在**（如 Joomla CVE-2015-8562 为 web + mysql），"靶场 = compose 项目"的模型天然覆盖单/多两种情况。
- **官方 vulhub 的 compose 文件基本不写 `container_name`。**
